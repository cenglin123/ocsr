# OCSR 系统主线与设计边界

## 目标

OCSR 解决宿主框架内建子代理不能跨厂商换模型、机械任务使用昂贵主模型、评审上下文受主对话污染的问题。它以一次性 `opencode run` 调用派发自包含任务，以文件系统证据回收产物。

## 核心设计决策

1. **OCSR 是执行后端，不是工作流引擎。** 收敛判定、预算门、轮次和归档由 converge 等上层流程负责。
2. **默认一次投递、文件回收。** CLI session 续接是版本相关能力，不作为共享上下文机制。
3. **残差注入优先于上下文搬运。** Prompt 必须明确任务、输入、输出、格式、边界和执行证据。
4. **确定性证据优先于代理自述。** 文件存在、非空、数量和抽样内容共同构成验收。
5. **保持文档型实现。** 现有已知问题均可由 `SKILL.md` 和离线验证脚本覆盖；没有运行时失败证据前不新增 wrapper。2026-07-24 手写重复事件证明派发链路需固化为 CLI 工具（非运行时 wrapper）；`scripts/ocsr_dispatch.py` 定位为一次性 CLI 工具，与"常驻 daemon、通用 runner"非目标不冲突。

   2026-08-09/10 的两次收敛失败（终局决策记账两次不同错法、分组编号两次误传）构成新的运行时失败证据，据此新增 `run --spec` 步骤运行器。**需诚实承认：这是一次显著的能力扩展**——从「派发 worker」扩展到「编排多步 DAG」；`hook` 步骤可执行 spec 中声明的任意外部命令（包括 `python -c "<任意代码>"`，校验层不做命令白名单）。**该能力在语义上触碰了「通用 runner」非目标的边界**，下方非目标条款的措辞未作任何修改、排除力保持不变。

   接受这一扩展的理由：(a) `hook` 是编排流程对接外部预算门与验收脚本的必要通道；(b) spec 由 orchestrator 撰写，`hook` 的 argv 来源可审计；(c) 步骤类型封闭为 `dispatch`/`hook`/`pause`/`assert` 四种，运行期由 `frozenset` 强制，不提供用户自定义函数类步骤；(d) **不提供安全沙箱**——spec 及其调用的命令必须当作可信输入对待，这与下方第一条非目标一致。新增任何步骤类型仍须重新审视本条并走独立复查——**该约束依赖人执行，不是代码级强制**。

   > 本段的表述经 2026-08-10 两位跨 family 独立治理评审（`deepseek-thinking` / `mimo`）否决了两版更宽松的写法后定稿。被否决的版本试图论证「本实现不属于被排除之物」，评审一致判为 `loosening`——「用接口描述替代能力约束，是把『我们选择这样设计』说成『我们不能做别的』」。此处保留其结论：**承认触碰边界，而不是把边界改成不包括自己。**

## 角色边界

- 顶层 orchestrator 负责拆解、预算披露、prompt 残差、产物验收和跨 worker 汇总。
- OCSR worker 只处理被授予的自包含任务，不拥有上层计划状态。
- Reviewer 必须是与作者上下文隔离的真实新调用；不能由 orchestrator inline 代写后标记为 fresh。
- 当 OCSR 被 converge 调用时，每一次 spawn 必须和 converge 的 reserve/settle 及证据账本一一对应。

## 非目标

- 不提供文件系统或网络安全隔离。
- 不提供常驻 daemon、通用 runner 或跨模型共享内存。
- 不替代宿主对副作用操作的授权和安全控制。
- 不把模型输出质量转化为无需复核的信任承诺。
